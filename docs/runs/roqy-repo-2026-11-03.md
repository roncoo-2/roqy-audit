# roqy infra readiness audit — run 2 (infra-readiness-audit skill, first run)

Date: 2026-11-03. Repo: /root/roqy @ 14cbfef. Static repo review only, no live cloud identity (roqy runs Docker on a single VPS, no Terraform/AWS).

## Inventory

- Runtime: Next.js app in Docker (docker-compose.yml), Caddy/NPM proxy on VPS, Supabase (managed), Sentry, Umami analytics (self-hosted, same compose).
- IaC: none. Deploys = GitHub Actions SSH to VPS, git pull + docker compose up -d --build.
- CI: deploy.yml (push main → build+lint+deploy), pr-agent.yml (PR agent with OPENAI_KEY).
- Secrets: .env gitignored; secrets.enc.yaml + gsc-key.enc.json SOPS/age encrypted, tracked in git.
- Monitoring: Sentry (app errors), healthcheck.sh cron every 1m (auto-restart app container), goaccess cron for access logs.
- Backups: /root/scripts/backup.sh, daily full 02:00, weekly/monthly tiers, /backups/{system,supabase,...}.
- Not applicable: Terraform state/drift (no IaC), cloud IAM (no cloud account), cost guardrails in cloud (flat VPS + managed services).

## Findings

### F1 — confirmed, P1: plaintext Umami DB password + APP_SECRET committed to git
Evidence: docker-compose.yml lines 12, 30 (`POSTGRES_PASSWORD: umam... (redacted)`, `APP_SECRET: roqy... (redacted)`). In git history since 082489d.
Consequence: anyone with repo read access gets Umami DB creds. Umami DB is bound to the compose network only, so blast radius is low, but it is a real credential in plaintext history while the rest of the repo uses SOPS.
Fix: move both to .env (`${UMAMI_DB_PASSWORD}`), rotate values, 1-2h. Good first task.

### F2 — confirmed, P1: deploy to prod with no review gate
Evidence: deploy.yml `on: push: branches: [main]`. Any direct push to main (or a merged PR) auto-builds and SSH-deploys as root. Branch protection not visible from repo (needs_validation at org/repo settings level).
Consequence: one bad push = prod down; no approval step. For a solo founder this is a deliberate tradeoff, but it is the top gap a first DevOps hire would close.
Fix: GitHub branch protection on main (require PR + 1 approval or at least require CI green), 30min.

### F3 — confirmed, P2: third-party Actions not SHA-pinned
Evidence: deploy.yml uses appleboy/ssh-action@v1.2.0; pr-agent.yml uses the-pr-agent/pr-agent@main with `contents: write` and GITHUB_TOKEN.
Consequence: a compromised or renamed tag/main of these actions runs with your token. pr-agent@main + contents:write is the sharper edge.
Fix: pin both to commit SHAs, drop `contents: write` from pr-agent if not needed, 1h.

### F4 — confirmed, P2: backups never restore-tested
Evidence: backup.sh writes /backups/{system,supabase}/daily|weekly|monthly; no restore script found (`grep -l restore` empty).
Consequence: backup you cannot restore is not a backup. Supabase is the customer-data store.
Fix: quarterly restore drill of one supabase dump into a scratch container, 2h. Good first task.

### F5 — needs_validation: alerting when prod is down
Evidence: healthcheck.sh restarts the container but nothing pages you. Sentry covers app errors, not downtime.
Consequence: site can be down for hours with nobody noticing (restart loop or VPS-level failure is not covered).
Fix: free uptime monitor (UptimeRobot/Better Stack) on https://roqy.io with email/Telegram alert, 30min. Check first whether one already exists outside the repo.

## Rejected (checked, not findings)

- Secrets in git: .env ignored; secrets.enc.yaml and gsc-key.enc.json are real SOPS/age ciphertext, not plaintext.
- Rate limiter clientIp spoofing: fixed since run-1 (cf-connecting-ip first, XFF last).
- Long-lived keys in CI: deploy uses SSH key secret, no AWS keys.
- No backups: backups exist with retention tiers.

## First-30-days plan for a DevOps hire (suggested)

1. Week 1: F5 uptime alert, F1 rotate Umami creds out of git.
2. Week 2: F2 branch protection + CI-required on main.
3. Week 3: F3 pin actions to SHAs, least-privilege pr-agent.
4. Week 4: F4 restore drill + document runbook.
